# ระเบียบวิธีของ Uyari

[English](../../METHODOLOGY.md) · [Español](../es/METHODOLOGY.md) · [Português](../pt/METHODOLOGY.md) · [Français](../fr/METHODOLOGY.md) · [Deutsch](../de/METHODOLOGY.md) · [Italiano](../it/METHODOLOGY.md) · [हिन्दी](../hi/METHODOLOGY.md) · **ไทย**

Uyari เป็นโครงสร้างข้อมูลและชุดเครื่องมือฝึกโมเดลแบบเปิด ที่เปลี่ยนคำแปลและเสียงบันทึกของชุมชนเองให้เป็นโมเดล
ระหว่างภาษาของชนพื้นเมืองหรือภาษาอื่นที่ยังขาดการรองรับ กับภาษาราชการที่ผู้พูดภาษานั้นต้องใช้
การเพิ่มภาษาคือการเพิ่มโฟลเดอร์ การเพิ่มข้อมูลคือการเพิ่มโฟลเดอร์ข้างในนั้น ไม่มีใครต้องแก้โค้ด
โมเดลของ Meta เป็นชุดเทคโนโลยีตั้งต้น (default stack)

เหตุผลเบื้องหลังการตัดสินใจเชิงโครงสร้างอยู่ใน [`docs/decisions/`](../../docs/decisions/)
ปัญหาที่โครงการนี้แก้ พร้อมตัวเลขและแหล่งที่มา อยู่ใน [`PROBLEM.md`](PROBLEM.md)

## 1. เป้าหมายและขอบเขต

**ห้ากรณีการใช้งานต่อหนึ่งคู่ภาษา:**

| # | กรณีการใช้งาน | โมเดล |
|---|---|---|
| 1 | ข้อความภาษาของชนพื้นเมือง → ข้อความภาษาราชการ | MT |
| 2 | ข้อความภาษาราชการ → ข้อความภาษาของชนพื้นเมือง | MT |
| 3 | เสียงพูดภาษาของชนพื้นเมือง → เสียงพูดภาษาราชการ | ASR → MT → TTS |
| 4 | เสียงพูดภาษาราชการ → เสียงพูดภาษาของชนพื้นเมือง | ASR → MT → TTS |
| 5 | เสียงพูดภาษาของชนพื้นเมือง → ข้อความภาษาของชนพื้นเมือง (speech-to-text) | ASR |

**คู่ภาษาแรกคือ ชาวี ↔ สเปน** (`cbt_Latn`, glottocode `chay1248`; เปรู) เป็นคู่แรกเพราะงานได้เริ่มที่นั่นแล้ว
ด้วยเรื่องสุขภาพมารดา ([`PROBLEM.md` §6](PROBLEM.md)) ไม่ใช่เพราะมีสิ่งใดเฉพาะเจาะจงกับคู่นี้ สิ่งที่มีอยู่สำหรับคู่นี้:

* ชิ้นข้อความ (chunk) หลักภาษาสเปน 11,977 รายการ (สังเคราะห์ จากเมทริกซ์การออกแบบใน `primary/spa_Latn/matrix.yaml`)
* คำแปลภาษาชาวีโดยคน 3,578 รายการ ของ chunk 3,575 รายการในนั้น เป็นงานที่ว่าจ้าง แบ่งเป็นการมีส่วนร่วมสามครั้ง
* chunk ชุดเดียวกัน 11,977 รายการในภาษาอังกฤษ แปลด้วยเครื่องจากภาษาสเปนโดยใช้ id ของ chunk เดิม
  ดังนั้นคำแปลภาษาชาวีทุกรายการจึงจับคู่กับภาษาอังกฤษได้ด้วย
* ยังไม่มีเสียงบันทึกภาษาชาวี เส้นทางของเสียง (ตัวตรวจสอบ, build, ไปป์ไลน์ ASR/TTS)
  ทดสอบกับชุดข้อมูลทดสอบสังเคราะห์ที่ติดป้ายกำกับไว้ (`qaa_Latn`) และ `NEEDS.md` ขอเสียงบันทึก

| อยู่ในขอบเขต | อยู่นอกขอบเขต |
|---|---|
| ภาษาใดก็ได้ที่มีระบบเขียน รูปแบบไฟล์รองรับทุกอักษรใน ISO 15924 (จนถึงตอนนี้ทดสอบแล้วเฉพาะอักษรละติน) | ภาษาที่มีแต่การพูด (รูปแบบไฟล์เก็บเสียงที่ยังไม่ถอดความได้ แต่ยังไม่มีไปป์ไลน์ใดใช้) |
| ภาษาราชการเป็นภาษาหลัก (primary): ภาษาสเปน (สร้างด้วยโมเดล) และภาษาอังกฤษ (แปลด้วยเครื่องจากภาษาสเปน) ภาษาอื่น (โปรตุเกส ฝรั่งเศส ฮินดี ไทย …) ใช้กลไกเดียวกัน | การวิจัยภาษาถิ่น: วิธภาษาเป็นป้ายกำกับของการมีส่วนร่วม |
| คำแปลและเสียงบันทึกโดยคน; ข้อความที่เครื่องเขียนมีได้เฉพาะฝั่งภาษาราชการ และต้องติดป้ายกำกับ | การแปลด้วยเครื่องที่นำเสนอว่าเป็นงานของคน |
| ภาษาหนึ่งเข้าร่วมได้เมื่อชุมชนนำข้อมูลมาและมีผู้ดูแลภาษา (steward) | บริการ inference สำหรับใช้งานจริง (production); เดโมเป็นเพียงเดโม |

## 2. หลักการ

1. **การมีส่วนร่วมคือหน่วยหลัก** ข้อมูลถูกจัดเก็บเป็นโฟลเดอร์การมีส่วนร่วม แต่ละโฟลเดอร์มีที่มา (provenance)
   สัญญาอนุญาต และความยินยอมของตัวเอง การรวมข้อมูลเกิดขึ้นเฉพาะใน build และ recipe เท่านั้น ไม่ใช่ด้วยการย้ายไฟล์
2. **ใช้ ID ที่คงที่ ไม่ใช้ตำแหน่ง** id ของ chunk เป็นเลขฐานสิบหก 32 หลักและไม่นำกลับมาใช้ซ้ำ
   (ผู้แปลทำงานจาก id ชุดเดียวกันนี้) จึงแบ่งหรือเรียงไฟล์ได้โดยไม่ทำให้การอ้างอิงเสีย
3. **การมีส่วนร่วมที่ merge แล้วจะไม่ถูกแก้ไข** การแก้ข้อผิดพลาดคือการมีส่วนร่วมใหม่ที่ระบุว่าแทนที่อะไร
4. **คนเป็นผู้แปลและพูด เครื่องร่างได้เฉพาะฝั่งภาษาราชการ และต้องบอกว่าเครื่องเป็นผู้ร่าง**
   chunk สังเคราะห์ทุกรายการระบุชื่อโมเดลที่เขียนมัน (`gen_model`, `provider`, `prompt_version`)
5. **ความยินยอมและการถอนข้อมูลคือข้อมูล** การมีส่วนร่วมทุกครั้งมีสัญญาอนุญาตและการอ้างอิงความยินยอม
   การถอนข้อมูลคือแถวหนึ่งใน CSV ที่ build ครั้งถัดไปจะนำไปใช้
6. **รหัสมาตรฐาน ชื่อที่เข้าใจง่าย build ที่ทำซ้ำได้** ภาษาระบุด้วย ISO 639-3 บวกอักษร (`cbt_Latn`)
   ซึ่งเป็นแท็กโมเดลของ Meta แท็ก build เดียวกันให้ค่าแฮชของเนื้อหาเดียวกันบนทุกระบบปฏิบัติการ
7. **ข้อมูลของชุมชนจะไม่ออกจากฮาร์ดแวร์ของเราไปยังโมเดลที่อาจนำข้อมูลไปฝึก** ทุกโมเดลประกาศ `data_policy`
   และโค้ดจะปฏิเสธการส่งข้อความภาษาของชนพื้นเมืองไปยังโมเดลระดับ Contributor ที่บุคคลภายนอกให้บริการ
8. **API แบบเสียเงินเป็นตัวเลือก และผู้ใช้เป็นผู้จ่ายเอง** CLI ใช้คีย์ของคุณเอง เดโมขอคีย์จากผู้เข้าชมแต่ละคน
   ถ้าไม่มีก็จะรันเฉพาะโมเดลแบบเปิดที่ fine-tune แล้ว

**ผลที่ตามมาข้อหนึ่ง** การแบ่งชุดข้อมูล (split) เป็นคุณสมบัติของ chunk หลัก ซึ่งทุกภาษาใช้ร่วมกัน
และกำหนดเป็นราย **กลุ่มประโยคถอดความ (paraphrase group)** (ประโยคถอดความที่ใกล้เคียงกันราว 10 ประโยค
ซึ่งได้จากคำขอสร้างข้อความครั้งเดียว) ดังนั้นไม่มีโมเดลใดเห็นประโยคถอดความของประโยคทดสอบระหว่างการฝึก

## 3. แบบจำลองข้อมูล

| เอนทิตี | คีย์ | ต้องมี |
|---|---|---|
| chunk หลัก | `chunk_id` (เลขฐานสิบหก 32 หลัก) | ข้อความ, split, ที่มา (origin), สถานะ; ทุกคอลัมน์ของเมทริกซ์การออกแบบที่ตัวสร้างข้อความบันทึกไว้ |
| ภาษา | `<iso639-3>_<Script>` | glottocode, ชื่อที่แสดง, ผู้ดูแลภาษา, ผู้มีอำนาจของชุมชน, อะพอสทรอฟีรูปมาตรฐาน |
| การมีส่วนร่วม | `<YYYY-MM>_<org>_<nnnn>` | ผู้มีส่วนร่วม (นามแฝง), สัญญาอนุญาต, ความยินยอม, ที่มา (provenance), วันที่เก็บข้อมูล, วิธภาษา |
| แถวคู่ภาษา | (การมีส่วนร่วม, chunk_id) | ข้อความ, translator_id (นามแฝง); `replaces` ไม่บังคับ |
| แถวเสียง | (การมีส่วนร่วม, ไฟล์) | ผู้พูด, ลีลาการพูด; chunk_id หรือคำถอดความ |
| ผู้พูด | (การมีส่วนร่วม, speaker_id) | ช่วงอายุ, การอ้างอิงความยินยอม |
| build | `data-YYYY.MM[-rN]` | หนึ่งตารางต่องานต่อภาษา, manifest พร้อมค่าแฮชของไฟล์และของเนื้อหา |
| recipe | ไฟล์ | build, ภาษา, โมเดลพื้นฐาน, วิธีการ, ไฮเปอร์พารามิเตอร์ |
| การ์ดโมเดล (model card) | `name@vX.Y` | build, recipe, สัญญาอนุญาตของโมเดลพื้นฐาน, คะแนน validation เทียบกับ retrieval floor, ผล test ที่วัดครั้งเดียว |

แถวเสียง: ถ้ามี `chunk_id` และ `transcript` ว่าง หมายความว่าผู้พูดอ่านคำแปลของ chunk นั้นจากการมีส่วนร่วมเดียวกัน
ถ้า `chunk_id` ว่างแต่มี `transcript` คือการพูดโดยธรรมชาติ (กำหนด split ตามผู้พูด) ถ้าว่างทั้งคู่จะเก็บไว้แต่ไม่ใช้
ชุดคำศัพท์ปิด (closed vocabulary) อยู่ใน `schemas/` และตัวตรวจสอบจะปฏิเสธค่าอื่นทั้งหมด

## 4. คลังข้อความหลัก (primary corpus)

คลังข้อความหลักคือชุดประโยคภาษาราชการที่ทุกภาษาแปล ปัจจุบันเป็นภาษาสเปน (`primary/spa_Latn/`)

**สิ่งที่มีอยู่** ชุดแรก `2026-06_opus48_0001.csv`: chunk 10,000 รายการ สร้างขึ้นในเดือนมิถุนายน 2026 ด้วย
Claude Opus 4.8 ครอบคลุม 4 จาก 15 ด้าน (domain) ของเมทริกซ์ และสถานการณ์ย่อย 37 สถานการณ์
ทุกแถวเก็บช่องเมทริกซ์ของตัวเองไว้ (ด้าน, สถานการณ์ย่อย, ระดับภาษา, วัจนกรรม, กาล, ขั้วบอกเล่า/ปฏิเสธ, บุรุษ,
ช่วงความยาว, ลักษณะผู้พูด, น้ำเสียง, ข้อความต่อเนื่อง, คำยึด (anchor words), `source_custom_id`)

**การสร้างเพิ่มด้วยโมเดลของ Meta** `uyari generate` คงสิ่งเหล่านี้ของชุดนั้นไว้: เมทริกซ์ การวนแบบ round-robin
ไปตามกาล/ขั้ว/บุรุษ คำยึด แผนงานบนดิสก์ที่มีสถานะรายหน่วยและรันซ้ำได้โดยผลไม่เปลี่ยน (idempotent) คีย์กลุ่ม `custom_id`
การแยกวิเคราะห์ (parsing) การตรวจสอบความถูกต้อง และการตัดข้อมูลซ้ำ รวมถึง **prompt ที่เหมือนเดิมทุกประการ**
(ตรึงไว้ที่ `prompt_version` เดียว) เพื่อให้การเปรียบเทียบวัดที่ตัวโมเดล ไม่ใช่การแก้ prompt
การสร้างใหม่ 200 ช่องด้วย Muse Spark 1.3 Contributor มีค่าใช้จ่าย 3.3% ของเดิมต่อ chunk 1,000 รายการ
โดยได้คำตอบที่มีรูปแบบถูกต้อง 100% และข้อความหลากหลายขึ้นเล็กน้อย (`reports/gen-comparison.md`)
ส่วน Muse Glimmer บน GPU ของเราเองทำได้โดยไม่มีค่า API ก่อนส่ง `--estimate` จะแสดงค่าใช้จ่าย แต่ละการรันมีเพดาน
และทุกการเรียกถูกบันทึกไว้ในสมุดบัญชี (ledger)

**การประมวลผลภายหลัง** NFC และช่องว่าง; 1–120 คำ และอยู่ในช่วงความยาวของหน่วยนั้น ±30%; คำศัพท์แบบเมืองที่ห้ามใช้;
การตรวจภาษา; การตัดข้อความซ้ำแบบตรงทุกตัวอักษร และข้อความเกือบซ้ำด้วย embedding (cosine 0.92 แบ่งบล็อกตามด้าน)
เทียบกับคลังข้อความหลักทั้งหมด; คนสุ่มอ่าน 2% ต่อชุด (`uyari primary sample`) และชุดที่ถูกปฏิเสธเกิน 5% จะถูกถอนออก

**การแบ่งชุดข้อมูล (split)** การกำหนดครั้งแรก: ชุด validation และ test มี chunk ที่แปลแล้วชุดละราว 300 รายการ
โดยเลือกเป็นกลุ่มประโยคถอดความทั้งกลุ่มจากกลุ่มที่แปลแล้ว แบ่งชั้นตามด้าน (stratified) และเรียงลำดับตามค่าแฮช
กลุ่มใหม่: กลุ่มที่สร้างช่องเดิมขึ้นใหม่จะรับ split ของช่องนั้น กลุ่มอื่นกำหนดตามค่าแฮช (5% / 5%)
เมื่อเขียนแล้วจะตรึงไว้ ไม่เปลี่ยนอีก

**คลังข้อความหลักเพิ่มเติม** คลังภาษาอังกฤษ (`primary/eng_Latn`) ใช้ id ของ chunk ร่วมกับคลังภาษาสเปน:
`uyari primary translate` แปล chunk ทั้ง 11,977 รายการด้วยเครื่องโดยใช้ Muse Spark 1.3 Contributor เสียค่าใช้จ่าย US$ 0.19
ติดป้ายกำกับ `origin=machine_translated` และคัดลอก split, ด้าน และกลุ่มประโยคถอดความมาจากภาษาสเปน
ภาษาราชการอื่นจะเพิ่มด้วยวิธีเดียวกัน

## 5. การเพิ่มภาษา

หนึ่งโฟลเดอร์ `languages/<iso639-3>_<Script>/` ที่มี `language.yaml` และ `README.md` ตัวตรวจสอบจะยอมรับเมื่อรหัสทุกตัว
หาเจอใน `registry/` (ยอมรับรหัสสำหรับใช้ภายใน ISO 639-3 `qaa`–`qtz`) และมีการระบุชื่อผู้ดูแลภาษา ฟิลด์:
`id, iso639_3, script, glottocode, display_name, iso_name, primary, steward, community_authority, apostrophe,
apostrophe_variants, training_orthography, trainer` ตัวอักษรที่เครื่องมือมักทำให้เพี้ยนจะประกาศไว้ครั้งเดียว:
ในภาษาชาวี เสียงกักที่เส้นเสียง (glottal stop) เป็นตัวอักษรตัวหนึ่ง รูปมาตรฐานคือ `ʼ` (U+02BC)
และตัวตรวจสอบจะแสดงรายการอักขระที่เป็นรูปแปรพร้อมวิธีแก้

## 6. การมีส่วนร่วม

ดู [`contributing/`](../../contributing/) (อังกฤษ สเปน โปรตุเกส ฝรั่งเศส เยอรมัน อิตาลี ฮินดี ไทย)
หนึ่งโฟลเดอร์ หนึ่ง pull request หนึ่งภาษา หนึ่งวิธภาษา หนึ่งสัญญาอนุญาต หนึ่งการอ้างอิงความยินยอม:
`contribution.yaml`, `pairs.csv`, `audio.csv`, `speakers.csv`, `wav/` การมีส่วนร่วมที่มีไม่ครบทุกส่วนเป็นเรื่องปกติ
build จะอนุมานว่าโฟลเดอร์มีอะไรบ้างจากไฟล์ที่มีอยู่

## 7. การตรวจทาน

มีสามด่าน: **ตัวตรวจสอบ (validator)** (CI ทุก PR), **Gatekeeper** (Muse Glimmer บน GPU ของเราเอง
เขียนรีวิวเป็นภาษาทำงานของผู้ดูแลภาษา ซึ่งสำหรับภาษาชาวีคือภาษาสเปน) และ **ผู้ดูแลภาษา (steward)** (คนที่พูดภาษานั้นได้)
Gatekeeper ตรวจจับสิ่งที่ไม่ผ่านตัวตรวจสอบ ข้อความภาษาราชการที่ถูกวางในคอลัมน์ภาษาของชนพื้นเมือง
แถวที่คัดลอกมาจากการมีส่วนร่วมที่ยอมรับแล้ว และข้อความที่ไม่เหมือนคู่ภาษาที่ยอมรับแล้ว
จากนั้นแนะนำให้ merge ส่งกลับ หรือส่งต่อให้พิจารณาในระดับสูงขึ้น (escalate) (ด้านสุขภาพและความยินยอมจะ escalate เสมอ)
Gatekeeper **ไม่ได้** ตรวจจับการแปลด้วยเครื่อง ผู้มีส่วนร่วมต้องรับรองว่าไม่ได้ส่งผลลัพธ์จากเครื่องมาเป็นงานของคน

## 8. Build

`uyari build --tag data-YYYY.MM` อ่านการมีส่วนร่วมทั้งหมด ใช้ `replaces` ข้ามการมีส่วนร่วมที่ถูกเพิกถอน
และการถอนข้อมูลที่มีผลในหรือก่อนวันที่ `--as-of` ปรับข้อความให้เป็นมาตรฐาน (normalize) เชื่อม split และด้านเข้ามา
แล้วเขียน `builds/<tag>/<lang>/{mt,asr,tts}.parquet` (train + validation) และ `*.test.parquet` (test)
พร้อม `MANIFEST.json`: git commit, การมีส่วนร่วมที่รวมและไม่รวมพร้อมเหตุผล, แถวที่ถูกตัดออกพร้อมเหตุผล,
จำนวนแถวต่อ split, สัญญาอนุญาต และสำหรับแต่ละตาราง ค่า `sha256` ของไฟล์และ `content_sha256` แบบ canonical
ข้อมูลที่ขาดจะถูกอนุมานเอง ไม่ต้องประกาศ ไฟล์ Parquet ไม่อยู่ใน git แท็กใช้สร้างขึ้นใหม่ได้

## 9. เอเจนต์

| เอเจนต์ | ตัวกระตุ้น | ตัดสินใจ | เขียน |
|---|---|---|---|
| **Gatekeeper** | PR เข้า `contributions/` | merge / ส่งกลับ / escalate (แนะนำเท่านั้น) | รีวิวบน PR และร่าง `review.yaml` |
| **Trainer** | merge เข้า `main` (runner GPU ที่โฮสต์เอง) หรือสั่งด้วยมือ | ควรสร้าง build ใหม่หรือไม่ (ภาษาใหม่ หรือคู่ภาษาเพิ่มขึ้น ≥10%); promote เฉพาะเมื่อทุกทิศทางชนะ retrieval floor **และ** ในทิศทางที่ทั้งสองโมเดลมีร่วมกัน chrF++ บน validation ดีขึ้น ≥0.5 เทียบกับโมเดลปัจจุบันที่ให้คะแนนใหม่บน build เดียวกัน (หรือโมเดลที่เสนอเพิ่มทิศทางใหม่และคะแนนลดลงไม่เกิน 0.5) | manifest ของ build, การ์ดโมเดล, `scores.json`, `models/registry.yaml`, `NEEDS.md`, pull request หนึ่งรายการ |
| Interpreter | (หลัง MVP) | | |

ข้อจำกัดป้องกัน: ไม่มีเอเจนต์ใด merge ไม่มีเอเจนต์ใดอ่าน split ทดสอบก่อนการ promote ชุด test ให้คะแนนเพียงครั้งเดียวต่อเวอร์ชันโมเดล
ทุกการตัดสินใจเป็นหนึ่งบรรทัดบน PR หรือบนการ์ดโมเดล พร้อมตัวเลขที่นำไปสู่การตัดสินใจนั้น

## 10. การฝึกและการประเมินผล

recipe ใน `recipes/` เป็นการตั้งค่าเพียงแหล่งเดียว โมเดลเดียวต่อหนึ่ง backend ครอบคลุมทุกภาษาราชการที่จับคู่กับภาษาของชนพื้นเมือง
(ปัจจุบันคือภาษาสเปนและภาษาอังกฤษ: สี่ทิศทาง) และแต่ละทิศทางให้คะแนนบนคู่ภาษาของตัวเอง โมเดลอ้างอิงสำหรับข้อความ:

* **Muse Glimmer 30B, QLoRA** (Unsloth, 4-bit, r=16, ความยาวสูงสุด 512, batch 1 × 16, 3 epoch): โมเดลหลัก รันบน RTX 4090 ของเรา
* **NLLB-200 1.3B, fine-tune เต็มรูปแบบ** (โทเค็นภาษาใหม่ตั้งค่าเริ่มต้นจากภาษาที่ใกล้เคียง; `quy_Latn` สำหรับภาษาชาวี):
  baseline ที่เร็ว และฝึกบน RTX 3060 12 GB แบบ bf16 ล้วนได้ด้วย
* **Retrieval floor (เกณฑ์ขั้นต่ำจากการค้นคืน):** คำแปลโดยคนของประโยคฝึกที่ใกล้เคียงที่สุด รันในเครื่อง ไม่มีค่าใช้จ่าย

เดโมให้บริการเฉพาะโมเดลที่ fine-tune แล้วเหล่านี้: Glimmer เป็นค่าเริ่มต้นเมื่อฝึกเสร็จ NLLB เป็นโหมดเร็ว
และการ์ดโมเดลจะบอกว่าตัวไหนได้คะแนนสูงกว่า

| งาน | คะแนน | การตรวจโดยคน |
|---|---|---|
| ข้อความเป็นข้อความ | chrF++ แยกตามทิศทาง (รายงาน BLEU แต่ไม่ใช้เป็นเป้าหมายในการปรับ) | เจ้าของภาษาสองคนให้คะแนน 100 ประโยค เมื่อหาคนได้ |
| เสียงพูดเป็นข้อความ | CER (รายงาน WER) | ความยอมรับได้ของคำถอดความบน 50 คลิป |
| ข้อความเป็นเสียงพูด | CER แบบไป-กลับผ่าน ASR | ความเป็นธรรมชาติ 1–5 |
| เสียงพูดเป็นเสียงพูด | chrF++ ของผลลัพธ์หลังผ่าน ASR | ความสำเร็จของงานในบทสนทนาที่เขียนบทไว้ |

COMET และตัวชี้วัดอื่นที่เรียนรู้จากข้อมูล จะไม่ถูกเชื่อถือสำหรับการแปลเข้าสู่ภาษาของชนพื้นเมือง
จนกว่าจะได้รับการยืนยันเทียบกับการตัดสินของคน

## 12. ค่าใช้จ่าย

* **รันในเครื่องเป็นค่าเริ่มต้น** การฝึก การประเมินผล Gatekeeper และเดโม รันบน GPU ของเราเองโดยไม่มีค่า API
* **ใช้คีย์ของคุณเอง** ทุกอย่างที่เรียก API แบบเสียเงินจะใช้คีย์ Meta ของผู้เรียกเอง: CLI อ่าน `META_API_KEY`
  เดโมขอคีย์จากผู้เข้าชม ใช้เฉพาะกับคำขอนั้นและไม่เก็บไว้เลย และไม่หันไปใช้คีย์ของเซิร์ฟเวอร์แทน
* **ประมาณการก่อนใช้จ่าย** ราคาอยู่ใน `config/llm.yaml` ทุกคำสั่ง LLM จะประมาณค่าใช้จ่ายก่อนส่ง
  (ค่าประมาณจาก tiktoken × 1.2) ปริมาณการใช้จริงของทุกการเรียกอยู่ใน `.uyari/ledger.jsonl`
  และแต่ละการรันมีเพดานตายตัว (`generate` $1, `transcribe` $2 ส่วนอย่างอื่น $0 เพราะรันในเครื่อง)
  งบประมาณพัฒนาของโครงการเองสำหรับ API ที่บุคคลภายนอกให้บริการคือ USD 150
